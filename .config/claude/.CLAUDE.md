# Claude Code Configuration

## Memory

When saving memories or context to files, write in English regardless of the
conversation language.

## Answering vs. acting

A question asks for an answer, not for changes. When the ask doesn't imply an
edit, answer it and say what you would change.

## Verification

Ground factual claims in a source checked this session — docs, tool output, the
code, git history, the live system — not recall. Confirm an option is supported
in the *target* context (ecosystem, runtime, plan tier), not merely documented
somewhere. If verification is impractical, say so and label the claim unverified.
A zero-result search is evidence about the query, not about the world: never
assert that something does not exist from one. Enumerate the space or broaden
the query first, otherwise label the negative unverified.

## Environment

Nix manages this machine. Install tools by adding them to the flake or Home
Manager config, never with `npm -g` / `pip` / `cargo install`.

## Design principles

Prefer simplicity over pathological correctness. YAGNI, KISS, DRY. Avoid
backward-compat shims or fallback paths unless they add no branching.

## Editing

Don't delete pre-existing dead code. Mention it instead.

Write a comment only when it carries what the code cannot: a constraint
from outside this file, a non-obvious reason a choice was made, or a trap
the next reader will otherwise hit. Before adding one, ask what a reader
who already has the code in front of them still doesn't know. If the
answer is nothing, don't write it.

Never narrate a change. "Moved from X", "used to be Y", "replaces Z"
belong in the commit message, not the file. Never restate what the line
below already says, and don't duplicate a commit body into a comment —
the copy in the file is the one that goes stale.

When a comment must explain a choice, give the reason that stays true
rather than the circumstance that will rot. Match the comment density of
the surrounding code.
